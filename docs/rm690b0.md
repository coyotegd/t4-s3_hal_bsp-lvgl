# RM690B0 AMOLED Display Driver - Complete Guide

## Overview

This document provides comprehensive implementation details for the RM690B0 AMOLED display driver on the LilyGo T4-S3 board. The RM690B0 uses a custom QSPI protocol that differs from standard SPI displays, requiring specific implementation techniques to achieve optimal performance and artifact-free rotation.

**Key Features:**

- 450×600 physical resolution (480×600 driver capacity)
- QSPI interface with custom protocol
- Hardware-accelerated DMA transfers
- Async flush implementation for optimal performance
- Support for all four rotation angles (0°, 90°, 180°, 270°)

### Display Controller Specifications

**RM690B0 Technical Details:**

- Single-chip AMOLED controller/driver with integrated display RAM
- Maximum resolution: 480RGB × 600 pixels
- Color depth: 16.7M colors (24-bit RGB888), 4096 colors (12-bit), 8 colors
- Interface support: MIPI DSI, 8-bit MPU, SPI, DUAL-SPI, QUAD-SPI
- Voltage requirements:
  - VDDI (Interface): 1.65V ~ 3.3V
  - VDD (Core): 2.70V ~ 3.60V
  - AVDD (OLED Drive): 4.5V ~ 6.5V
  - VGH/VGL (Gate): ±12V range
- Operating temperature: -40°C to +85°C

**Supported Resolutions (Partial List):**

The RM690B0 driver IC supports multiple display resolutions through window addressing:

- 480×600 (full capacity)
- 480×480, 400×400, 360×480
- 320×480, 320×320, 272×480
- 240×320, 240×240, 180×360
- 180×540, 128×432

**T4-S3 Implementation:** Uses 450×600 visible area with QUAD-SPI interface

## Custom QSPI Protocol

### Protocol Overview

The RM690B0 on the LilyGo T4-S3 uses a non-standard QSPI protocol to wrap commands and data. This is likely due to the specific interface configuration (IM[1:0]=10) and the controller's internal logic. Unlike standard SPI displays, this driver requires custom QSPI packet formatting.

**Interface Mode Selection (IM[1:0] pins):**

The RM690B0 supports multiple interface modes selected via IM[1:0] hardware pins:

| IM[1:0] | Interface Mode        | Notes                                     |
| ------- | --------------------- | ----------------------------------------- |
| 00      | MIPI DSI              | 1/2 data lane, up to 550Mbps              |
| 01      | 8-bit MPU (80-series) | Parallel interface with CS/DCX/WR/RD      |
| 10      | 4-wire SPI / QSPI     | **T4-S3 configuration**                   |
| 11      | 3-wire SPI            | Serial data + clock (no separate D/C pin) |

**T4-S3 Board:** Uses IM[1:0]=10 (4-wire SPI/QSPI mode)

### Pixel Format Support

The RM690B0 supports multiple pixel formats:

- **RGB888 (24-bit):** Full 16.7M colors, 3 bytes per pixel
- **RGB666 (18-bit):** 262K colors, 3 bytes per pixel (6 bits per channel)
- **RGB565 (16-bit):** 65K colors, 2 bytes per pixel (5R-6G-5B)

**T4-S3 Implementation:** RGB565 (16-bit) for optimal performance and memory usage

### Protocol Details

**Write Command:**

- Opcode: `0x02` (1-bit transmission)
- Address: `0x00CC00` (1-bit transmission), where `CC` is the command byte
- Data: Command parameters (1-bit transmission)
- Mode: 1-1-1 (Standard SPI)

**Write Data (Pixels):**

- Opcode: `0x32` (1-bit transmission)
- Address: `0x002C00` (1-bit transmission), where `0x2C` is the RAMWR command
- Data: Pixel data (4-bit QSPI transmission)
- Mode: 1-1-4 (Quad Page Program style)

### Implementation Strategy

The custom QSPI protocol was reverse-engineered to work with the T4-S3 board configuration:

1. Standard SPI commands (1-bit) are NOT sufficient for all operations
2. The driver uses `spi_device_polling_transmit` with `SPI_TRANS_MODE_QIO` for pixel data
3. Commands are wrapped in custom QSPI packets using the 0x02/0x32 opcodes

## Driver Implementation

### Configuration Parameters

**SPI Mode:**

- QIO (`SPI_TRANS_MODE_QIO`) is used for pixel data to enable 4-bit transfer
- Significantly improves throughput compared to standard SPI

**CS Control:**

- Hardware CS (`PIN_NUM_QSPI_CS`) is managed by the SPI driver
- Critical for DMA and queued transactions
- Ensures proper timing for QSPI operations

**Transfer Size:**

- Max transfer size: 64KB (`65536`)
- Accommodates LVGL draw buffer (~36KB) in a single DMA transaction
- Reduces overhead and improves performance

### Core Driver Functions

**Reference:** `components/rm690b0/rm690b0.c`

The driver component handles:

- Low-level QSPI transactions using custom 0x02/0x32 opcodes
- Initialization sequence (Sleep Out, Display On)
- `rm690b0_set_window` for defining drawing regions
- `rm690b0_draw_bitmap` for graphics rendering
- `rm690b0_set_rotation` for display orientation

### Async Flush Implementation

The driver implements `rm690b0_flush_async` using `spi_device_queue_transmit`, allowing optimal CPU utilization:

**Benefits:**

- CPU returns to LVGL immediately after queuing the transfer
- SPI peripheral transmits data via DMA in the background
- Next rendering chunk can be prepared while current chunk transfers

**Safety Considerations:**

- Implementation relies on LVGL's single-threaded rendering loop
- `flush_cb` is not called again until `lv_display_flush_ready` is invoked in the transaction callback
- `spi_transaction_ext_t` and context structures are static to persist during async transfer
- Safe due to serialized access guaranteed by LVGL's architecture

## Rotation & Display Configuration

### The Problem: Graphical Artifacts

During development, significant graphical artifacts appeared when rotating to Landscape modes (90° and 270°):

1. **Skew/Italics Effect**: Image appeared slanted or wrapped incorrectly
2. **Redraw Lines**: Single-pixel lines on button release or partial redraws
3. **Alignment Issues**: Misaligned pixels during GRAM access

### The Solution: Symmetric Even Resolution

The root cause was identified as an alignment issue within the display controller's GRAM access when the `MV` (Row/Column Exchange) bit is set in the `MADCTL` register.

**Requirements for Artifact-Free Rotation:**

1. **Even Resolutions**: Both width and height must be even numbers in landscape modes
2. **Even Offsets**: X and Y offsets must be even numbers to ensure proper byte alignment during QSPI transfers

### Portrait Modes (0° & 180°)

*These modes are less sensitive to alignment and work with the native odd-width resolution.*

| Parameter         | Value         | Notes                          |
| ----------------- | ------------- | ------------------------------ |
| **Resolution**    | **450 × 600** | Native visible area            |
| **Offset X**      | **14**        | Centers the image horizontally |
| **Offset Y**      | **4**         | Centers the image vertically   |
| **MADCTL (0°)**   | `0x00`        | Default orientation            |
| **MADCTL (180°)** | `MX \| MY`    | Both X and Y inverted          |

### Landscape Modes (90° & 270°)

*These modes require strict even-number alignment.*

| Parameter         | Value         | Notes                                             |
| ----------------- | ------------- | ------------------------------------------------- |
| **Resolution**    | **600 × 450** | **Must be even** (adjusted from native 594×450)   |
| **Offset X**      | **20**        | **Must be even** for proper alignment             |
| **Offset Y**      | **12**        | **Must be even** (fixed redraw artifacts)         |
| **MADCTL (90°)**  | `MV \| MY`    | Row/Col Exchange + Y-Mirror                       |
| **MADCTL (270°)** | `MV \| MX`    | Row/Col Exchange + X-Mirror                       |

### Code Implementation

```c
void rm690b0_set_rotation(rm690b0_rotation_t rot) {
    // CRITICAL: Use even numbers for resolution and offsets in landscape modes
    switch (rot) {
        case RM690B0_ROTATION_0:
        case RM690B0_ROTATION_180:
            current_width = 450;
            current_height = 600;
            offset_x = 14;
            offset_y = 4;
            break;

        case RM690B0_ROTATION_90:
        case RM690B0_ROTATION_270:
            current_width = 600;
            current_height = 450;
            offset_x = 20;
            offset_y = 12;
            break;
    }
    // ... MADCTL register configuration follows
}
```

### Troubleshooting History

**Attempt 1 (Standard Swap):**

- Swapping X/Y to 594×459 caused severe skewing
- Confirmed that odd dimensions cause GRAM alignment issues

**Attempt 2 (Resolution Tuning):**

- Reducing resolution helped but didn't eliminate artifacts
- Symmetry enforcement was required

**Attempt 3 (Offset Tuning):**

- Using `offset_y = 11` (odd) left single pixel line artifacts during partial redraws
- Changing to `offset_y = 12` (even) completely resolved the issue

## Power Sequence

### Initialization Steps

1. **Enable Power (GPIO 9)**
   - Initialize GPIO 9 as output
   - Set HIGH to power the display and PMIC rails
   - Wait ≥10ms for power rails to stabilize

2. **Power Supply Sequencing**
   - VDDI (Interface power): 1.65V ~ 3.3V
   - VDD (Core power): 2.70V ~ 3.60V
   - No strict ordering required between VDDI and VDD
   - Both must reach 90% of target voltage before reset

3. **Reset Pulse (GPIO 13)**
   - Active Low pulse
   - Timing from datasheet:
     - Hold LOW for ≥10ms after power stable
     - After HIGH: Wait ≥20ms before sending commands
   - Ensures clean controller initialization

4. **Display Initialization Commands**
   - Wait ≥1ms after reset before first command
   - Send initialization sequence:
     - SWRESET (0x01): Software Reset
     - SLPOUT (0x11): Sleep Out - wait ≥50ms
     - DISPON (0x29): Display On - wait 1 frame (~17ms @ 60Hz)

### Power-On Sequence Timing (from Datasheet)

```text
VDDI/VDD      ────┐  ╔════════════════════════════════
              ────┘  ╚═ (≥10ms stabilization)

RESX (GPIO13) ════╗  ┌─────╔═══════════════════════════
              ────╚══╝─────╝
                   ≥10ms  ≥20ms

Commands               │   SLPOUT  │   DISPON  │ Frame data
                       └──►├─50ms─►├──17ms────►
                        ≥1ms
```

### Power-Off Sequence

For proper shutdown:

1. Send DISPOFF (0x28): Display Off
2. Wait ≥5 frames (≥83ms @ 60Hz)
3. Send SLPIN (0x10): Enter Sleep Mode
4. Wait ≥10ms
5. Pull RESX LOW (optional)
6. Disable power supplies (VDDI, VDD, VBAT)

### Common Display Commands

| Command | Code | Parameters | Description |
| --- | --- | --- | --- |
| NOP | 0x00 | 0 | No operation |
| SWRESET | 0x01 | 0 | Software reset (wait ≥50ms after) |
| SLPIN | 0x10 | 0 | Enter sleep mode (low power) |
| SLPOUT | 0x11 | 0 | Exit sleep mode (wait ≥50ms after) |
| INVOFF | 0x20 | 0 | Display inversion off |
| INVON | 0x21 | 0 | Display inversion on |
| DISPOFF | 0x28 | 0 | Display off (blanking) |
| DISPON | 0x29 | 0 | Display on |
| CASET | 0x2A | 4 | Column address set (X coordinates) |

| RDID3 | 0xDC | 0 | Read ID3 (Driver ID) |

**Note:** Commands are sent using the custom QSPI protocol (opcode 0x02) on T4-S3.

### MADCTL Register (0x36) - Memory Access Control

The MADCTL register controls display orientation and color order:

| Bit | Name | Function |
| --- | ---- | -------- |
| 7 | MY | Row address order (0=top→bottom, 1=bottom→top) |
| 6 | MX | Column address order (0=left→right, 1=right→left) |
| 5 | MV | Row/Column exchange (0=normal, 1=swapped; enables rotation) |
| 4 | ML | Vertical refresh order (0=top→bottom, 1=bottom→top) |
| 3 | RGB | RGB/BGR order (0=RGB, 1=BGR) |
| 2 | MH | Horizontal refresh order (0=left→right, 1=right→left) |
| 1:0 | - | Reserved (should be 0) |

**Common Rotation Values:**

- 0° (Portrait): `0x00` (MY=0, MX=0, MV=0)
- 90° (Landscape): `0x60` (MY=0, MX=1, MV=1)
- 180° (Portrait inverted): `0xC0` (MY=1, MX=1, MV=0)
- 270° (Landscape inverted): `0xA0` (MY=1, MX=0, MV=1)

**Implementation Note:** The T4-S3 driver uses these values with additional offset adjustments for the 450×600 visible area.

## PMIC Configuration (SY6970)

The LilyGo T4-S3 board includes an SY6970 Power Management IC that requires specific configuration:

### Critical Settings

1. **Watchdog Timer**
   - **Must be disabled** to prevent power cycling
   - Default watchdog can reset the system unexpectedly
   - Disable during board initialization

2. **OTG Power**
   - **Should be disabled** unless specifically needed
   - Saves power and prevents conflicts
   - Not required for normal display operation

### Implementation Note

The PMIC configuration is handled during board-level initialization before the display driver is initialized. Ensure proper I2C communication is established with the SY6970 to configure these settings.

## Summary

### Key Takeaways

1. **Custom QSPI Protocol**: The RM690B0 requires non-standard packet formatting (0x02/0x32 opcodes)
2. **Even Resolution Requirement**: Landscape modes must use even dimensions and offsets to prevent artifacts
3. **Async DMA Transfers**: Implementation provides optimal performance through background transfers
4. **Power Sequence Matters**: GPIO 9 must be HIGH before any display operations
5. **PMIC Configuration**: Watchdog timer must be disabled to ensure stable operation

## Additional Notes

This implementation represents a working solution that was developed through careful analysis of the display controller's behavior and systematic troubleshooting of rotation artifacts. The custom QSPI protocol and even-resolution requirements are specific to this hardware configuration and may not apply to other RM690B0 implementations.

**Key Electrical Specifications (from Datasheet):**

- **Operating Temperature:** -40°C to +85°C (junction)
- **Storage Temperature:** -55°C to +125°C
- **VDDI Input:** 1.65V ~ 3.3V (interface logic)
- **VDD Input:** 2.70V ~ 3.60V (core)
- **AVDD Output:** 4.5V ~ 6.5V (OLED drive - via internal boost)
- **VGH/VGL Range:** +12V / -12V (gate drive - via charge pump)
- **MIPI Max Speed:** 550Mbps total (2 lanes) for RGB888
- **Frame Rate:** Configurable, typically 60Hz
- **Display RAM:** Integrated (480×600×24 bits = 864KB)

The RM690B0 includes integrated DC/DC converters and charge pumps to generate all necessary OLED drive voltages from a single VDD supply, simplifying board design.
